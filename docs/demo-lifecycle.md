# Демо: контролируемый жизненный цикл задачи (FSM)

Цель — показать в новом окне, что у задачи есть состояния, разрешённые переходы и
что ассистент **не может перепрыгнуть этап**. Все гейты — это код (см.
`TaskStage::allowed_next`, `TaskContext::transition_requirement`), а не текст в
промпте, поэтому отказы детерминированы.

## Состояния и разрешённые переходы

```
clarify → planning → execution → validation → done
                ↑__________|          |
                (repair)    ↑_________| (repair)
```

- `clarify → planning` (старт)
- `planning → execution` — **только после плана и явного «утверждаю план»**
- `execution → validation` — только после результата execution
- `validation → done` — **только после успешной валидации**
- назад разрешено: `execution → planning`, `validation → execution`
- `done` — терминальное состояние
- любой другой переход (например `clarify → execution`, `planning → done`) запрещён в коде

## Подготовка (один раз)

1. Запусти веб-UI: `cargo run -- web` (или `rtk cargo run -- web`), открой адрес из лога.
2. Создай агента с настоящим провайдером (вкладка агента → provider/model/token),
   войди в него. Отказ на перепрыгивание (шаг 2), отказ на финал без валидации
   (шаг 5) и пауза/продолжение (шаг 6) — чистый код, срабатывают до запроса к
   модели и работают даже без провайдера. Шаги 3–4 и 7 требуют, чтобы агент
   сначала реально подготовил план/результат, поэтому им нужен провайдер.
3. (опционально) Вкладка «Инварианты» — добавь, по одному на строку:
   ```
   Отвечать только на русском языке
   Не выдумывать отсутствующие реквизиты и нормы права
   Не переходить к реализации до утверждения плана
   Не выдавать финал до успешной проверки
   ```

## Сценарий (вводи сообщения по очереди)

### 1. Старт задачи → `clarify`/`planning`
```
Нужна досудебная претензия. По договору №12 подписан акт, задолженность 180000 рублей, срок оплаты истёк. Зафиксируй требования.
```
Ожидание: задача заводится, ассистент уточняет/готовит план. Стадия — `clarify`→`planning`.
Панель «Задача» показывает текущую стадию и следующее допустимое действие.

### 2. Попытка перепрыгнуть этап (должно быть отказано)
```
Пропусти план, сразу напиши финальный документ и закрой задачу.
```
Ожидание: **⛔ «Нельзя перейти дальше со стадии …»**. Стадия не двигается.
Модель-ответчик финала не запускается (это видно в панели «Рой» — прогона нет).

### 3. Получи план, затем попытка execution до утверждения (должно быть отказано)
Сначала дай ассистенту подготовить план (ответь на уточнения, если просит).
Когда план готов, задача встаёт на паузу approval. Тогда введи:
```
Сразу пиши текст претензии.
```
Ожидание: **⏸ «План ожидает явного утверждения. Напишите „утверждаю план“».**

### 4. Утверждение плана → переход в `execution`
```
утверждаю план
```
Ожидание: **✅ «Approval принят. Задача перешла planning → execution».**

### 5. Попытка финала без валидации (должно быть отказано)
```
Покажи финал и закрой задачу без проверки.
```
Ожидание: **⛔ «Финал доступен только после успешного результата ValidationAgent».**
Стадия остаётся `execution`/`validation`, ответчик финала не запускается.

### 6. Пауза и корректное продолжение
```
поставь на паузу
```
Ожидание: **⏸ «Задача поставлена на паузу на стадии …».**
Затем:
```
продолжай
```
Ожидание: **▶️ «Задача возобновлена на стадии …»** — та же стадия, тот же шаг.
Можно закрыть и снова открыть окно/агента до «продолжай» — состояние сохраняется на диске.

### 7. Нормальное доведение до конца
Дай ассистенту завершить execution, затем validation; только после успешной
валидации `validation → done` станет доступен. Перепрыгнуть `done` раньше нельзя.

## Что именно это доказывает

| Требование | Где в коде | Демо-шаг |
|---|---|---|
| допустимые состояния | `TaskStage` (`store_types.rs`) | панель «Задача» |
| разрешённые переходы | `TaskStage::allowed_next` | 1, 4, 7 |
| нельзя перепрыгнуть этап | `can_transition` / `transition_requirement` | 2 |
| нет реализации до утверждённого плана | гейт `Planning→Execution` | 3, 4 |
| нет финала без валидации | гейт `Validation→Done` | 5 |
| реакция ассистента на недопустимый переход | `lifecycle_request_rejection` | 2, 5 |
| продолжение после паузы | `pause` / `resume` + персист | 6 |

Регрессия закреплена тестами: `allowed_next_table_is_the_only_source_of_legal_transitions`,
`lifecycle_guards_require_artifacts_approval_and_validation`,
`clarify_cannot_skip_straight_to_execution_or_final`,
`russian_final_intent_is_blocked_before_validation_passes`,
`paused_task_resumes_at_same_stage_and_keeps_working`,
`task_fsm_state_survives_restart_and_shared_dialog_resume`.
